# Methodology (as implemented through milestone B, plus pilot preparation)

Background: `KV Cache Precision — Experiment Design.docx`. This file records what the code actually does.

## Protocol: `post_prefill_conversion/v1`

Every example follows one procedure (`src/kvstudy/runner.py`):

1. Render the full prompt once:
   - the model's chat template with the fixed system prompt;
   - the benchmark input as the user turn;
   - the generation prompt, with Qwen3 thinking disabled (`enable_thinking=False`);
   - RULER's answer prefix appended after the generation prompt, as RULER's own model templates do.
2. Tokenize the full rendered string in a single pass and find the context/question boundary at token level (`backends/mlx.py: render_prompt`).
3. Prefill `ids[:boundary]` in BF16, in chunks of 2048 tokens. This is the **reference cache** and is never modified.
4. For each method:
   1. Make an independent branch of the reference cache (`branch_cache`), using new array objects sliced to the cache offset.
   2. Apply the method's conversion to the branch.
   3. Process `ids[boundary:]` (the question plus the assistant prefix) through the branch.
   4. Decode greedily up to `max_new_tokens`, stopping at EOS.
   5. Score, save the record, and release the branch.

Because the question is read after conversion, retrieval must go through the converted context. MLX-LM stores keys after RoPE, so `key_position: post_rope` holds by construction.

A future protocol that quantizes during prefill is a different protocol and will get a different `protocol_id`.

### Token boundary

The boundary is the first token whose character start is at or after the question's character offset. If one token spans the boundary, it is placed on the question side, and the record's `metadata.boundary_straddled` is set.

With Qwen3 and RULER inputs this always happens: the context's final `.` and the question's leading `\n` form one token `.\n`. The converted context therefore excludes one character of punctuation, and that token is processed with the question.

Prefilling `ids[:b]` and then `ids[b:]` reproduces the single-pass tokenization exactly. This is tested in `tests/test_integration.py`. Split prefill also reproduces the single-pass logits, which is tested in `tests/test_backend_mlx.py`.

### Branch isolation

`tests/test_backend_mlx.py` checks that the reference cache is unchanged after generating through a branch. It also checks that two branches neither affect each other nor produce different outputs. It covers cache offsets both on and off MLX-LM's 256-token allocation step.

## RULER

- **Data.** Examples are generated by upstream `scripts/data/prepare.py` from the pinned NVIDIA/RULER clone, with:
  - the HF tokenizer of the model under test, so lengths are exact for that tokenizer;
  - `--model_template_type base`, so the chat template is applied by kvstudy rather than by RULER;
  - the task settings from upstream `synthetic.yaml`.

  RULER sizes the haystack so that input tokens plus `tokens_to_generate` ≈ the target length, counted without a chat template. Records keep the actual rendered token counts (`n_input_tokens`, `n_context_tokens`, `n_question_tokens`), which include template overhead.
- **Context/question split.** An upstream `input` is split at the last occurrence of the template text that follows `{context}`, taken from upstream `constants.py`. For single-needle NIAH, the same singular rewrite as `niah.py` is applied. Preparation fails if the marker is missing, if the question part is implausibly long, or if a reference answer is not inside the context.
- **Splits.** Each example gets a deterministic 20/80 dev/test split by hash of `source_id`. Each synthetic example is its own source. Each split's manifest is written once, with a `.sha256` sidecar, and preparation refuses to overwrite an existing manifest.
- **Overlap guard.** `prepare ruler --disjoint-from <manifests>` reads earlier manifests (never writes them) and refuses the new set if:
  - an example ID already exists with different content;
  - identical context and question would land in a different split;
  - a `source_id` would appear in two splits.

  The same checks run within the new set. Example IDs are `ruler/<task>/<length>/<index>`, so a new manifest generated with the same seed and more samples reproduces the earlier examples under the same IDs and splits. The check confirms this rather than assuming it.
- **Essay haystack.** `niah_multikey_1`, `niah_multivalue` and `niah_multiquery` use RULER's Paul Graham essay haystack. Upstream downloads it from the web rather than pinning it, so each such example records the file's sha256 as `metadata.haystack_sha256`. Within one length, every essay example uses the same essay prefix with different needles. The haystack is a shared distractor, not a per-example source.
- **Scoring.** Scoring uses `postprocess_pred`, `string_match_all`, and `string_match_part`, copied verbatim from upstream, and maps task family to metric exactly as upstream `TASKS` does. Scores are computed per example on a 0–100 scale. Upstream rounds each call to 2 decimals, so a mean of per-example scores can differ from upstream's whole-set call by at most 0.005. `tests/test_integration.py` checks parity against the clone.

## Cache methods

### `identity` (BF16 baseline)

The branch is left untouched and stays BF16 throughout. The protected window does not apply to it.

### `uniform` (simulated)

Uniform conversion works as follows (`methods/uniform.py`):
- At the conversion point, every context token's K and V are replaced by `dequantize(quantize(x))`. The bit widths `key_bits` and `value_bits` are set independently.
- This uses MLX affine quantization (`mx.quantize`), with groups of `group_size` along the head dimension, i.e. per token.
- Because this is the same rounding MLX's real quantized storage uses, quality in simulation equals quality in the format.
- The branch holds dequantized BF16 values, so the resident memory and speed of the simulation say nothing about a quantized system.

Only `axis: per_token` is implemented. Per-channel (KIVI-style) key groups come later.

### Protected window (`protocol.protected_window`)

This policy is shared by every compressed method:
- Tokens appended after conversion (the question, then each generated token) are fake-quantized at `precision_bits` as they enter the cache.
- Once more than `tokens` are held, the oldest are demoted to the method's own key/value bits (`overflow: demote_oldest`). Demotion re-quantizes the window-precision values, as a real system holding only the window-precision copy would.
- Tokens are never promoted. A window below a method's precision is rejected.
- The cache class deliberately has no `bits` attribute, so mlx-lm keeps using its standard attention over the dequantized values.

With RULER inputs (≈40–65 question tokens, ≤128 generated) the 512-token window never overflows.

## Memory accounting

Affine quantization needs, per token, layer and KV head:
- the packed payload: head_dim × bits / 8 bytes for K and for V;
- one BF16 scale and one BF16 bias per group: 4 bytes × head_dim / group_size, for K and for V.

So the effective bits per element are `b + 32/g`, as in the experiment design. This matches the buffer sizes `mx.quantize` produces, which is tested.

- `cache_bytes_estimated`: bytes at the conversion point (context tokens only). This is the quantity for equal-memory comparisons.
- `cache_bytes_estimated_final`: bytes after decode, counting protected-window tokens at window precision and demoted tokens at the method's precision.
- For `identity`, both are the analytic BF16 value, asserted equal to the cache's actual `nbytes`. For `uniform`, they are labelled `analytic_affine_simulated`: estimates, not measurements.

Position indices are not needed for uniform methods. They enter the accounting with selective precision (milestone D).

### Format verification

After conversion, layer 0's K and V are checked on a sample of up to 64 tokens against the bit width read from the cache object:
- values must have changed;
- the per-group error must be at most two nominal quantization steps. MLX shifts the grid so zero is exact, and BF16 output rounding adds error at 8 bits, so the error can exceed half a step;
- when `2^bits < group_size`, a group may hold at most `2^bits` distinct values.

A conversion that was skipped, or done at the wrong bit width, fails the run.

## Memory and timing in `quality_simulated` mode
- Timings (`prefill_context`, `branch_and_convert`, `question_and_decode`) are wall-clock values with no warm-up or repeats. They carry `timings_label`, which says they are not systems measurements.

## Failures

Exceptions become records with `status: failed` and a traceback. MLX Metal allocation errors become `status: oom`. Both have `score: null`. Summaries count them separately and exclude them from means.

## Resume

`kvstudy resume <run_dir>` reloads `resolved_config.yaml` and rebuilds the manifest fields that define the experiment:
- config hash and schema version;
- model and tokenizer files;
- packages;
- hardware and OS;
- dataset and evaluator fingerprints;
- execution, protocol, and system prompt;
- the methods index.

It also compares `code_fingerprint`: the sha256 of every `.py` file under `src/kvstudy/` as it is on disk, with a per-file digest. Uncommitted edits and untracked files change it, so a commit ID is not relied on. `analysis/` and `cli.py` are excluded, because they cannot change what a run produces. A mismatch names the changed files.

It refuses to continue if any of these differ. A run whose manifest predates a field, such as runs made before code fingerprinting, cannot be verified and is refused. The git state at resume is also recorded in the `resume_started` event.

Steps:
1. A final JSONL line without a newline (an interrupted write) is cut off, and the cut is logged as `interrupted_write_removed`.
2. Every (example, method) pair that already has a record is skipped. If only some methods of an example are missing, the example is prefilled again and only those methods run.
3. Failed and oom records are kept unless `--retry-failed` is given. A retry appends a new row with `attempt + 1`, and analysis uses the latest attempt per example. Rows are never overwritten.

## Analysis

`kvstudy analyze` (`analysis/compare.py`) reads only saved files. When the run has exactly one `identity` method, it writes `paired_vs_reference` to `comparisons/summary.json`. Each entry has a `scope`:
- `cell`: one task × context length;
- `pooled`: every pair of a benchmark, weighted per example, which is not a mean of cell means.

For each other method and scope, it reports:
- `n_pairs` and `n_sources`;
- `n_excluded`: examples where either side is not `ok`, or the reference is missing;
- the mean score of each side;
- `mean_diff` (method − reference) with `mean_diff_ci`;
- `flip_rate` (prediction text differs) with `flip_rate_ci`.

Pairs are matched on `example_id`.

Intervals are 95% percentile intervals from a paired cluster bootstrap: 10,000 resamples with fixed seed 0, recorded under `paired_vs_reference.bootstrap`.
- Each resample draws whole `source_id`s with replacement, and keeps every pair of a drawn source. Examples from one document are never split apart.
- For RULER each example is its own source, so this reduces to a per-example bootstrap.
- With fewer than two sources the interval is `null`.

McNemar tests and Holm correction come later.
